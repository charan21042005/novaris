2. Distributed Fraud Detection Engine for Fintech Transactions

Problem Statement: Real-time scoring of transactions for fraud risk before approval. Target users: payment processors, neobanks.

Core Architecture:

Event-driven pipeline: transaction → Kafka topic → stream processor scores it → decision service approves/flags → async audit log
Lambda architecture: real-time path (low-latency rules + lightweight model) + batch path (retrain model nightly on full history)

Tech Stack:

Frontend: React dashboard (Recharts/D3) for fraud analysts, real-time alerts via WebSocket
Backend: FastAPI (Python) for scoring service, Spring Boot/Go for transaction ingestion API, gRPC internally, REST externally
Databases: PostgreSQL (transactions, audit trail), Redis (feature cache, velocity checks — "5 transactions in 60s"), Pinecone/Milvus (embedding similarity for anomaly patterns)
AI/Data Pipeline: Kafka (event streaming), PyTorch/XGBoost model served via TorchServe or ONNX Runtime, feature store (Feast) to avoid train/serve skew
Cloud/DevOps: Kubernetes, Kafka on Confluent Cloud or self-managed on K8s, Terraform for IaC, Prometheus + Grafana for model drift/latency monitoring

Key Integrations: Stripe/Razorpay sandbox API, webhook-based alerting (Slack/email), JWT-based service-to-service auth.

Interview Talking Points:

Handling data consistency between real-time scoring and eventual batch retraining
Idempotency for transaction processing (avoiding double-charging on retry)
P99 latency optimization — why you cache features in Redis instead of hitting Postgres per request
Model drift detection and shadow deployment before promoting a new fraud model






Project 2 (Deep Dive): Distributed Real-Time Fraud Detection Engine
1. Refined Problem Statement

Payment processors need to approve/decline transactions in under 200-300ms while catching fraud patterns that evolve daily. The hard part isn't the model — it's the systems engineering: feature computation under latency pressure, avoiding train/serve skew, and handling millions of transactions/day without losing data.

Target users: Payment gateways, neobanks, e-commerce checkout systems, B2B fintech APIs.

2. End-to-End System Architecture
Client/Merchant → API Gateway → Transaction Ingestion Service
                                        │
                                        ▼
                                  Kafka (transactions topic)
                                        │
                        ┌───────────────┼───────────────┐
                        ▼               ▼               ▼
              Real-Time Scoring    Feature Enrichment   Audit/Storage
              Service (Flink/      Service (Redis        Consumer
              Python consumer)     feature lookups)      (→ Postgres)
                        │
                        ▼
              Decision Service (approve/decline/flag)
                        │
                        ▼
              Response → API Gateway → Client (sync, <300ms)

              [Async, parallel path]
              Flagged transactions → Review Queue → Analyst Dashboard
              Nightly batch job → Airflow → Retrain model → Model Registry

Key design patterns:

Event-driven architecture — transactions are events, not RPC calls, so you can replay/audit/reprocess
CQRS — the write path (ingest transaction) is separate from the read path (analyst dashboard queries)
Lambda architecture — real-time scoring (speed layer) + nightly batch retraining (batch layer) reconciled via a feature store
Circuit breaker — if the ML scoring service times out, fall back to rule-based scoring rather than blocking the transaction


3. Detailed Tech Stack
Frontend (Analyst Dashboard)
Layer	Choice	Why
Framework	React + TypeScript	Type safety for financial data
State	TanStack Query + Zustand	Server cache vs. UI state separation
Charts	Recharts / D3.js	Transaction volume, risk score distributions
Real-time	WebSocket (Socket.io)	Live fraud alerts pushed to analysts
Auth UI	Auth0 SDK or custom JWT flow	Role-based views (analyst vs. admin)


Backend & APIs
Layer	Choice	Why
Ingestion API	Go (Gin/Fiber) or Java (Spring Boot)	High-concurrency, low-latency requirement
Scoring Service	Python (FastAPI)	ML ecosystem access (PyTorch/XGBoost)
Internal comms	gRPC (Protobuf)	Faster serialization than JSON for service-to-service
External API	REST (OpenAPI spec)	Merchant-facing, needs to be widely consumable
Decision orchestration	Temporal.io or plain state machine	Manages multi-step approve/flag/review workflow reliably
Background workers	Celery (Python) or Go worker pool	Async audit logging, notification dispatch
Databases & Caching
Layer	Choice	Why
Transactional DB	PostgreSQL	ACID guarantees for financial records, audit trail
Feature cache	Redis	Sub-ms lookups for velocity checks ("txns in last 60s"), sliding window counters via Redis sorted sets
Vector/similarity	Pinecone or Milvus	Embedding-based similarity search for "transactions that look like known fraud patterns"
Feature store	Feast (open-source)	Guarantees same feature computation logic in training and serving — this is a major interview talking point
Time-series (optional)	TimescaleDB	For transaction volume trend analysis
AI/ML & Data Pipeline
Layer	Choice	Why
Streaming	Apache Kafka	Durable, replayable event log; decouples ingestion from scoring
Stream processing	Kafka Streams or Apache Flink	Windowed aggregations (rolling averages, velocity features)
Model (real-time)	XGBoost or LightGBM	Fast inference (<10ms), interpretable (SHAP values for analyst explainability)
Model (deep pattern)	PyTorch autoencoder or GNN	Catches novel fraud rings via transaction graph analysis (optional stretch goal — great interview differentiator)
Model serving	ONNX Runtime or TorchServe	Standardized, fast inference layer decoupled from training code
Orchestration	Apache Airflow	Nightly retraining DAG, feature backfills
Experiment tracking	MLflow	Model versioning, A/B comparison of model versions
Cloud, DevOps & Deployment
Layer	Choice	Why
Containerization	Docker	Standard
Orchestration	Kubernetes (EKS/GKE)	Autoscale scoring service based on Kafka consumer lag
IaC	Terraform	Reproducible infra, interview-relevant
CI/CD	GitHub Actions → ArgoCD (GitOps)	Automated test → build → deploy pipeline
Monitoring	Prometheus + Grafana	Latency (p50/p95/p99), throughput, error rates
Model monitoring	Evidently AI or custom drift detector	Detect when live data distribution diverges from training data
Logging	ELK stack or Loki	Centralized structured logs for debugging decisions
Key Integrations
Payment gateway sandbox: Stripe or Razorpay test mode for realistic transaction schemas
Alerting: Slack/PagerDuty webhook when fraud rate spikes
Auth: JWT for merchant API keys, mTLS for internal service-to-service calls
Notification: SendGrid/SES for flagged-transaction customer notifications


4. Interview Talking Points (What Makes This Stand Out)
Train/serve skew — explain how Feast ensures the exact same feature computation (e.g., "avg transaction amount last 7 days") is used in both training and real-time inference, avoiding silent accuracy degradation.
Latency budget breakdown — be ready to say: "API gateway: 10ms, feature fetch from Redis: 5ms, model inference: 15ms, decision logic: 5ms — total budget 200ms with headroom for network."
Idempotency — how you prevent double-scoring/double-charging on network retries (idempotency keys stored in Redis with TTL).
Backpressure handling — what happens when Kafka consumer lag grows during a traffic spike; explain autoscaling triggers.
Cold start problem — new merchants/users have no history; explain fallback to rule-based scoring until enough data accumulates.
Explainability — SHAP values so analysts (and regulators) can see why a transaction was flagged — critical in fintech.
Shadow deployment — how you test a new model version on live traffic without it affecting real decisions, before promoting it.
